Employee Attrition
Machine Learning Pipeline

How the model is trained, deployed through Heroku, and represented in the live Streamlit dashboard.

Presentation guide | Current implementation and future API roadmap

1. The business problem

Employee attrition can increase recruitment costs, remove organisational knowledge, and disrupt team performance.

Objective

Identify patterns linked with historical attrition and prioritise supportive retention conversations.

Output

An estimated probability that an employee belongs to the attrition class, converted into a risk band.

Responsible use

The score supports human decision-making. It is not a certainty, a diagnosis, or a reason to penalise an employee.

The .joblib file is an application artifact. It is machine-readable rather than presentation-readable; the notebook and this document explain what it contains.

3. Training pipeline

Cleaned CSV→ Feature selection→ Train/test split→ Preprocessing→ Logistic regression→ Evaluation→ Save pipeline
  • Target: AttritionBinary, where 0 means stayed and 1 means left.
  • Excluded: the target, duplicate label Attrition, and identifier EmployeeNumber.
  • Split: 80% training data and 20% test data, stratified and reproducible with random_state=42.

4. How the data is prepared

Numeric columns

Missing values are filled with the median, then values are standardised with StandardScaler.

Examples: income, age, distance, tenure, and satisfaction scores.

Categorical columns

Missing values are filled with the most frequent value, then categories are converted using one-hot encoding.

Examples: department, job role, overtime, and travel.

One pipeline

Preprocessing and classification are saved together, ensuring live predictions use the same transformations as training.

5. The model and its explanation

The classifier is a class-balanced logistic regression model. It produces a probability from 0 to 1.

ProbabilityRisk bandMeaning in the app
Below 0.30LowLower estimated risk in this model
0.30 to below 0.60MediumWorth monitoring and understanding context
0.60 or higherHighPriority for a supportive review

A positive coefficient is associated with higher predicted risk; a negative coefficient is associated with lower predicted risk. These relationships do not prove causation.

6. What the Joblib file contains

employee_attrition_pipeline.joblib stores the fitted pipeline after training.

Imputation settings+ Scaling settings+ Encoding categories+ Feature order+ Model coefficients

It is loaded by Python with Joblib. It should not be edited manually. Human-readable evidence comes from the notebook, charts, metrics, and future summary exports such as CSV or JSON.

7. From model to dashboard

app.py→ get_scored_data()→ get_model()→ load_or_train_model()→ predict_proba()→ Risk band
  • The app loads the cleaned dataset and the saved model.
  • The model applies its stored preprocessing to employee feature columns.
  • predict_proba(...) returns the estimated probability for class 1, meaning attrition.
  • The app adds Risk probability and Risk band columns to the displayed data.
  • Streamlit caching prevents unnecessary reloading during normal interaction.

8. What the user sees

Overview

Total employees, historical attrition rate, high-risk profile count, and workforce hotspots.

Charts

Attrition by job role and department, presented with interactive Plotly visualisations.

Risk triage

Employee or segment-level risk information that helps users prioritise investigation and support.

Actions

Evidence-led retention ideas connected to the observed patterns, not automatic employment decisions.

9. How Heroku runs the app

Merge to connected branch→ Heroku build→ Install requirements→ Run setup.sh→ Start Streamlit→ Live HTTPS URL

The Procfile starts the web process with:

web: sh setup.sh && streamlit run app.py

At startup, the app loads the dataset and model from the deployed release. A new model or code change becomes live after a successful redeployment and restart.

Heroku storage is ephemeral. Do not treat files generated at runtime as permanent storage. Version important model artifacts or use durable external storage.

10. Recommended live deployment lifecycle

  1. Update or validate the cleaned data.
  2. Retrain the model in the notebook when the data, features, or model logic changes.
  3. Evaluate the new model on a held-out test set.
  4. Save and version the compatible .joblib pipeline.
  5. Commit the model and code changes together.
  6. Merge to the Heroku-connected branch.
  7. Check the Heroku build logs and test the live dashboard.

This keeps the model artifact, feature logic, and app representation aligned.

11. Future: live API data

The current app reads a versioned CSV. A future production design could replace or supplement that source with a secure API.

HR system→ Authenticated API→ Validation layer→ Model pipeline→ Dashboard

API ingestion

Fetch employee records using HTTPS, authentication, pagination, and timeouts.

Schema validation

Confirm required columns, data types, allowed categories, and missing-value rules before prediction.

Operational safety

Use secrets management, access control, logging, retries, rate limits, and a safe fallback when the API is unavailable.

12. Future API architecture

A robust design would separate data retrieval from prediction:

api_client.py       # authenticates and retrieves current records
data_validation.py  # checks schema and cleans API responses
ml_model.py         # transforms data and predicts
dashboard_utils.py  # caches and prepares dashboard data
app.py              # presents results in Streamlit
  • Keep API credentials in Heroku Config Vars, never in Git.
  • Do not expose personal employee data in URLs, browser code, logs, or presentation screenshots.
  • Record the model version and prediction timestamp with each result.
  • Monitor input drift and model performance when confirmed outcomes become available.

13. Limitations and ethical safeguards

Uncertainty

A probability is an estimate based on historical patterns, not a guaranteed outcome.

Causation

Model coefficients show associations. They do not establish that changing one factor will prevent attrition.

Fairness

Review results for unfair impact across groups and avoid using the model as the sole basis for decisions.

Privacy

Restrict access, minimise personal data, and retain only what is necessary for the retention purpose.

14. Conclusion

PeoplePulse connects a reproducible machine-learning pipeline with an accessible business dashboard.

Train locally→ Save compatible pipeline→ Deploy with Heroku→ Score employee data→ Support retention action

The next step is to introduce a validated, authenticated live API while preserving the same preprocessing, model versioning, privacy, and human-oversight principles.
